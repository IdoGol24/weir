# weir-run

The canary runner checks whether a program exposes the credentials it
holds to a place outside your control: its telemetry, its console output,
the model provider (prompts and messages) or any other service or host. It
plants a unique fake credential (a canary) wherever a real one would live,
runs the program's own example flows against a local mock that records
every request and exports telemetry to a file, and asks `weir canary
judge` one question: did any planted value reach the capture, or a request
to anything but its own provider? Because the runner knows every value it
planted, the answer is an exact match in seven encoded forms, not a
pattern guess.

Its contract, and the judge's, is weir's
[`docs/canary.md`](https://github.com/IdoGol24/weir/blob/main/docs/canary.md).
This page is for the maintainer who adds the check to a project's CI,
and, in [The Claude Code check](#the-claude-code-check), for anyone who
runs Claude Code and wants to know whether their setup keeps their keys
out of it.

## The pieces

```text
weir-run run --config canary.toml
  1. plant   one fresh fake value per placement -> ledger (mode 0600, private temp dir)
  2. mock    127.0.0.1 only: OpenAI-compatible and Anthropic Messages model API,
             OAuth endpoints, OTLP/HTTP receiver, your project's own APIs;
             refuses every proxied request to another host
  3. flows   each under an empty environment plus an allowlist, URLs pointed at the mock,
             in a network namespace whose only network is loopback (Linux)
  4. capture OTLP/JSON lines + other telemetry bodies + each flow's stdout and stderr
             + every request the mock received, refused ones included
  5. judge   weir canary judge (weir-scan: opens no socket, starts no process)
  6. delete  the ledger and the capture
exit 0 clean and complete | 1 a canary leaked | 2 usage, input or runner error | 3 incomplete
```

- **The judge is weir-scan's**, called only through its command line. The
  runner never imports weir, and weir never imports the runner (both are
  import-linter contracts in the repository's `pyproject.toml`). The runner
  requires weir-scan 0.6.0 or later, the first release whose
  `weir canary judge` reads the ledger's `network` and `direct` records
  and takes `--requests` (the request sink);
  without a judge it exits 2 before running anything.
- **Local and offline.** The mock binds `127.0.0.1` on a port the OS picks;
  there is no option to bind anything else. Every flow gets the mock as its
  HTTP and HTTPS proxy, and the mock refuses every proxied request: a
  `CONNECT` or an absolute-URL request for any other host gets a 403, and
  nothing is forwarded, opened or resolved. On Linux every flow also runs
  in a network namespace with no route out, so a client that ignores proxy
  settings reaches nothing either (see [Network isolation](#network-isolation)).
- **Test-time only.** The runner is a dependency of your CI job, never of
  your program. The mock and the receiver exist only for one run.

## Fake data only

- Every value in a run is generated by the runner: the canaries it plants
  and the tokens its OAuth endpoints issue. Never put a real credential in
  a config, a flow's `env` or anywhere a flow reads it.
- Never point a flow at a real provider. Every API a flow calls must be the
  mock: the model API through `OPENAI_BASE_URL` or `ANTHROPIC_BASE_URL`,
  your project's own APIs through `[[mock.endpoint]]`, OAuth through the
  mock's endpoints.
- The ledger and the capture are deleted when the run ends. Do not copy
  them anywhere, and never commit one: a provider-shaped canary in a public
  repository is reported to the provider as a leaked key. Only the
  value-free report may be kept, for example as a CI artifact.
- In a CI job, check out with `persist-credentials: false` so the job token
  is not in the checkout a flow can read.

## Try the demo

The demo is one synthetic agent flow, standard library only: it gets an
OAuth token, asks the model (which calls its `web_search` tool), calls the
search API, sends the result back, and exports its spans over OTLP/HTTP.

```sh
weir-run run --config demo/canary.toml        # exits 0
weir-run run --config demo/canary-leak.toml   # exits 1
```

`canary-leak.toml` differs only in `DEMO_LEAK = "1"`, which makes the flow
record its search key and its HTTP Basic client credentials as span
attributes, put its request headers (with the access token) in a JSON
string attribute, and print the search key in a debug line. The run
reports each as a `LEAK` line by placement, file, line and form, and the
relayed debug line reads `debug: search key <canary:env.SEARCH_API_KEY>`.

## The config

```toml
[mock]
oauth = true                      # serve the OAuth endpoints (default false)
model_reply = "Done."             # the model's final answer
tool_calls = "each-offered-tool-once"   # or "none"

[mock.credential_fields]          # extra credential fields of built-in endpoints
model = ["header:api-key"]        # endpoints: model, oauth, otlp (otlp: header and query only)
                                  # model always has header:x-api-key, the Anthropic key header

[[mock.endpoint]]                 # one of your project's own APIs
id = "search"                     # served at {mock}/ep/search/...
credential_fields = ["header:x-api-key", "query:api_key", "body:api_key"]
status = 200
reply = '{"results": []}'
content_type = "application/json"
capture = false                   # true: keep request bodies as capture files

[[placement]]
id = "env.SEARCH_API_KEY"         # the variable is the id after "env."
kind = "env"                      # env | code
shape = "generic"                 # see Shapes
required = true                   # incomplete unless exercised or leaked
provider = "search"               # the mocked endpoint it belongs to: model, oauth, otlp or an endpoint id
provider_host = "api.search.example"   # its real host: a refused attempt to reach it is evidence

[[placement]]
id = "code.client.api_key"
kind = "code"
variable = "MY_VARIABLE"          # the flow reads this; omit it for CANARY_CODE_CLIENT_API_KEY
provider = "model"                # passed to the model client, so it belongs to the model API

[[flow]]
id = "quickstart"
command = ["{python}", "examples/quickstart.py"]   # {python}: the runner's interpreter
cwd = "."                         # relative to this file
timeout_seconds = 300
env = { SEARCH_BASE_URL = "{mock}/ep/search" }     # non-secret settings; {mock} is the mock
skip = "needs a GPU"              # optional: recorded as skipped, which is incomplete
```

Unknown tables and keys are errors (exit 2), so a typo cannot silently
drop a placement. Ids follow the contract's id rule (1 to 128 characters
from `[A-Za-z0-9._:#/-]`) and are unique.

### Placements

This release plants two kinds and mints a third (docs/canary.md,
"Placements and kinds"):

| kind | where the canary lives |
| --- | --- |
| `env` | the flow's environment, under the variable your software reads |
| `code` | a variable the runner names; the flow reads it and passes it explicitly to a constructor or call |
| `mock-oauth` | every authorization code, device code, access, refresh and ID token the mock's OAuth endpoints issue, as `runtime.oauth.<token>#<n>`; nothing to configure |

### Shapes

A canary is a provider's prefix followed by random `[A-Za-z0-9]`, so
software that checks a key's prefix or length accepts it. Each provider
shape matches the key pattern weir's catalog judges that provider's keys
by. No value ever contains `FAKE`, `TEST`, `EXAMPLE`, `DEMO`,
`PLACEHOLDER` or `REDACTED`, in any letter case.

| shape | prefix and body |
| --- | --- |
| `generic` | 40 characters, no prefix |
| `openai` | `sk-proj-` + 48 |
| `anthropic` | `sk-ant-api03-` + 93 |
| `github` | `ghp_` + 36 |
| `google` | `AIza` + 35 |
| `aws-access-key-id` | `AKIA` + 16 of `[A-Z0-9]` |

Values come from the CSPRNG, fresh each run. `--seed N` swaps in a
deterministic stream for reproducing a run locally; never use it in CI.

## What a flow receives

A flow starts from an empty environment, not the job's, and gets exactly:

| variables | value |
| --- | --- |
| `PATH` | the runner's `PATH` |
| `HOME`, `TMPDIR`, `TEMP`, `TMP` | a fresh private directory per flow (`USERPROFILE` too on Windows) |
| `LANG`, `PYTHONUTF8` | `C.UTF-8`, `1` |
| `SYSTEMROOT`, `PATHEXT` | Windows only, from the runner |
| `CANARY_MOCK_URL` | the mock's base URL, `http://127.0.0.1:<port>` |
| `OPENAI_BASE_URL`, `OPENAI_API_BASE` | `<mock>/v1` |
| `ANTHROPIC_BASE_URL` | `<mock>`: the Anthropic SDKs add `/v1/messages` themselves |
| `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_{TRACES,LOGS,METRICS}_ENDPOINT` | the mock's receiver |
| `OTEL_EXPORTER_OTLP_PROTOCOL` and the per-signal ones | `http/protobuf` |
| `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY` (both cases) | the mock, which refuses |
| `NO_PROXY`, `no_proxy` | `127.0.0.1,localhost` |
| each placement's variable | its canary |
| the flow's `env` | as written, `{mock}` replaced |

A real provider key in your CI secrets never reaches a flow. A flow's
leftover child processes are stopped when the flow ends.

## The mock

| path | what it is |
| --- | --- |
| `POST /v1/chat/completions` | Chat Completions, plain and streaming. With tools offered, turn one calls every tool once with a minimal schema-valid argument, so each tool's credentials are exercised; once tool results are in the conversation it answers `model_reply` |
| `POST /v1/responses` | Responses, plain and streaming, same script |
| `POST /v1/messages` | the Anthropic Messages API, plain and streaming (`message_start`, `ping`, `content_block_start`, `content_block_delta`, `content_block_stop`, `message_delta`, `message_stop`), same script: turn one answers with a `tool_use` block for every offered tool, and once the last user message carries `tool_result` blocks it answers `model_reply`. A query such as `?beta=true`, body fields it does not know and `system` entries between turns are accepted. The key goes in `x-api-key` |
| `HEAD`, `GET /api/hello` | a connectivity check on the model API's base URL: `200` |
| `POST /v1/embeddings`, `GET /v1/models` | fixed answers |
| `POST /v1/traces`, `/v1/logs`, `/v1/metrics` | the OTLP/HTTP receiver: protobuf or JSON, gzip or deflate |
| `GET /oauth/authorize` | redirects with a fresh code |
| `POST /oauth/token` | authorization code, refresh token, password, device code, client credentials, token exchange and JWT bearer grants; a refresh token where the grant usually has one, an ID token when the scope holds `openid` |
| `POST /oauth/device_authorization` | a fresh device code; the user code is not a credential |
| `GET /.well-known/openid-configuration` | discovery metadata pointing at the mock |
| `/ep/<id>/...` | a configured endpoint: its fixed reply |

Every supported grant succeeds, whatever it presents. The OAuth paths exist only with `oauth = true`.
Anything else is answered 404 and listed after the run.

**Requests are a sink.** The mock records every request it receives, a
refused one included, in `capture/requests.jsonl`: destination, method,
path, query, headers and body. The judge searches each request for every
canary and decides by the placement's own provider (`provider` and
`provider_host` above):

- in a credential field of a request to its own provider (its auth
  headers and the fields the endpoint declares), a canary is evidence that
  it was exercised, as a key in its own API's auth header should be;
- anywhere else it is a `LEAK` naming the sink and the field, for example
  `sink="model" at=body.messages[0].content` for a key pasted into a
  prompt, `sink="search"` for a key sent to the wrong one of your APIs, or
  `sink="collector.example (blocked)"` for a key in a plain-HTTP request
  to another host;
- a refused HTTPS `CONNECT` carries no visible content: it is listed as
  `blocked connection: <host>:<port>` and counted in the coverage, never a
  leak by itself.

A placement with neither a `provider` nor a `provider_host` belongs in no
request, so any request that holds it is a leak, and the runner says so
before any flow runs:
`placement <id> has no provider: any request holding it counts as a leak`.
A token the mock's OAuth endpoints issue belongs to those endpoints and to
every `[[mock.endpoint]]`.

**Credential fields.** Before any of these handles a request, the mock
inspects its credential fields: the whole `Authorization` and
`Proxy-Authorization` headers on every mocked endpoint, each endpoint's
declared fields, the model API's `x-api-key` header (the Anthropic
Messages API's key),
and on the OAuth endpoints the form fields `client_secret`,
`client_assertion`, `assertion`, `code`, `device_code`, `refresh_token`,
`subject_token`, `actor_token` and `password`. A field holding a canary in
any encoded form (a Basic credential included) is accounted for, and the
judge attributes it from the request capture. Any other non-empty value is
recorded as `unexpected.<endpoint>.<field>#<n>`, never in the ledger, and
makes the run incomplete: a flow that sends a credential no canary
accounts for has left the check's premise.

**The capture.** The receiver writes each export request decompressed, as
one OTLP/JSON line (trace and span ids in lowercase hex), under
`capture/otlp/`; its headers go to the request capture only. A body it
cannot decode is kept as its own capture file and a marker line makes the
run incomplete. Request bodies of an endpoint with `capture = true` and
each flow's stdout and stderr are swept capture files.

## Network isolation

On Linux, the runner runs the mock and every flow in an unprivileged user
and network namespace (what `unshare --user --net` makes) whose only
interface is loopback. The mock listens on `127.0.0.1` inside it, so flows
reach it as before, and nothing has a route to any other host. A flow
holds no capability in the namespace, so it cannot add one.

Every other address is routed to the namespace's own loopback, so a client
that ignores the proxy settings fails at once (connection refused, or a
failed name lookup) instead of hanging, and the runner sees the attempt:

| observed | reported as |
| --- | --- |
| a TCP connection opened to any address but loopback | `tcp`, the address and port |
| a UDP datagram sent to any address but loopback | `udp`, the address and port |
| a DNS query sent to any address, loopback included | `dns`, the name asked for |

Each distinct attempt makes the run incomplete, as
`incomplete: direct_connection <flow>=<protocol>:<target>`: isolation
stopped it, but what it would have sent was never seen. The runner's
output lists them as `network: blocked direct ...` lines. A blocked
datagram's payload, a DNS query included, is a swept capture file, so a
canary in it is a `LEAK` like any other.

Not observed: traffic on loopback, which never leaves; a name lookup made
through a host service over a Unix socket, such as systemd-resolved's NSS
module or nscd, which happens outside the namespace (the connection that
follows is still blocked and reported); an IPv6 attempt where the kernel
has IPv6 disabled, which fails with no packet; Unix-socket traffic to a
host service such as a Docker socket; anything a process the flow detached
does after the run.

Where the namespace cannot be made (not Linux; unprivileged user
namespaces disabled or restricted, as Ubuntu's
`kernel.apparmor_restrict_unprivileged_userns=1` does), the run goes ahead
as before, the runner's output says `network: not isolated (<why>)`, and
the report carries:

```text
network not isolated: direct connections were not observed
```

| option | `weir-run run` | pytest |
| --- | --- | --- |
| an unisolated run is incomplete (exit 3, `incomplete: network_not_isolated`) | `--require-isolation` | `--canary-require-isolation` |

Use `--require-isolation` in CI on Linux. A found leak still exits 1. A
flow that needs the host's network (installing packages, a database on the
host's loopback) does not work isolated: install first, or mock the
service. On a GitHub-hosted Ubuntu runner, allow unprivileged user
namespaces first:

```sh
sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0
```

## Output

- **stderr:** first, one line for each placement with neither a
  `provider` nor a `provider_host`; then each flow's status and its own
  stdout and stderr, relayed after the run with every encoded form of
  every canary replaced by `<canary:PLACEMENT-ID>`; whether the network
  was isolated, and each blocked direct attempt; refused egress and
  unmocked requests by count.
- **stdout:** the judge's text report: one `LEAK` line per hit, the
  not-exercised placements, the blocked destinations, the incomplete
  reasons, the coverage line, the network line and the result. It names
  placements, locations and sinks, never a value or a fragment of one.
- `--report FILE` also writes the judge's `canary-report/1` JSON.
- The exit code is the judge's, or 2 for the runner's own usage and
  configuration errors and any other failure of the run (an unwritable
  `--report`, a judge that times out). A runner fault never exits 1.

A clean result is evidence about the flows that ran and the placements
planted, not a statement that the program is safe. Read the coverage line:
a placement no flow exercised is printed as `not exercised`.

## The pytest plugin

Installing the runner registers a `canary_check` fixture (subprocess mode):

```python
def test_quickstart_exports_no_credentials(canary_check):
    canary_check.mock(oauth=True)
    search = canary_check.endpoint("search", credential_fields=["header:x-api-key"])
    canary_check.env("SEARCH_API_KEY", required=True, provider="search")
    variable = canary_check.code("code.client.api_key", provider="oauth")
    canary_check.run(["{python}", "examples/quickstart.py"], env={"SEARCH_BASE_URL": search})
    # teardown judges; the test fails on a leak or an incomplete run
```

Declare the mock and the endpoints, then the placements that name them as
their `provider`, first; the first `run`
plants the canaries and starts the mock. At teardown the plugin judges,
prints the redacted flow output and the report, deletes the ledger and the
capture, and fails the test unless the result is clean. To assert on the
result yourself, call `result = canary_check.judge()` (`result.code`,
`result.report`). The judge is the `weir` beside the interpreter or on
`PATH`; override the `canary_judge_command` fixture to use another. Flows
run isolated as under `weir-run run`; `--canary-require-isolation` is the
pytest option (see [Network isolation](#network-isolation)).

## The Claude Code check

Does my Claude Code setup keep my keys out? A `[claude_code]` config runs
the installed Claude Code once, headless (`claude -p`), with the settings
under test, and reports, secret by secret, which of the fake secrets it
planted the setup kept out and which reached the model, the telemetry,
another host or the console.

```toml
[claude_code]
key_owner = "anthropic"            # required to judge: "anthropic" or "gateway"
project = "."                      # its .claude directory and CLAUDE.md are under test
user_settings = "my-claude"        # optional: a copy of your ~/.claude, or of its settings.json
managed_settings = "policy"        # optional: a copy of /etc/claude-code, or of its settings file
executable = "claude"              # default: the first `claude` on PATH
timeout_seconds = 300
```

A `[claude_code]` config takes no other table: the runner plants the
secrets, scripts the model and runs the one flow itself.

```sh
weir-run run --config canary.toml
```

### What the run does

1. **A scratch project and a scratch home.** The project holds a short
   README and copies of your project's configuration:
   - from `.claude`, only what Claude Code reads as configuration:
     `settings.json`, `settings.local.json`, `hooks`, `commands`,
     `agents`, `skills`, `rules`, `output-styles` and `CLAUDE.md`, never
     the worktrees, sessions and other state Claude Code keeps there;
   - the memory files `CLAUDE.md` and `CLAUDE.local.md`, and every file
     inside the project they import (`@path`), as deep as Claude Code
     follows imports;
   - each script a hook starts, wherever it is in the project.

   A symbolic link whose target is inside the project is copied as that
   target; one that points outside the project, or nowhere, is left out,
   so a hook script behind it is missing and the run is incomplete.
   `settings.json` and `settings.local.json` are read wherever they point.

   `user_settings` becomes the scratch home's user settings: a settings
   file, or a copy of your `~/.claude` directory, of which the run takes
   the same configuration entries (never sessions, history or
   credentials) and the scripts its hooks start. `managed_settings` takes
   the place of the machine's managed settings directory
   (`/etc/claude-code`): a settings file, or a copy of that directory, with
   its `managed-settings.json`, its `managed-settings.d` drop-in files,
   its `hooks` and its `CLAUDE.md`. The verdict lists what it copied from
   each directory.

   Claude Code layers them as it would for you: for ordinary values,
   managed settings over local project settings over project settings
   over user settings, the managed drop-in files merged over
   `managed-settings.json` in name order; permission rules from all of
   them merge, and a deny in any file always wins over an allow. The
   verdict lists the files it applied, highest first. A settings file
   Claude Code skips as invalid (it says so in its debug log, which the
   run reads) is named as skipped, and none of its settings is counted as
   applied. Claude Code skips a project, local or user settings file with
   an invalid value, but keeps a managed one: it applies the rest of the
   file and reads the invalid value its own way, as on for some settings
   and as absent for others, mostly without saying so. So the managed
   values the check reads are taken only in the forms a live run showed
   Claude Code applies: `allowManagedHooksOnly` and `disableAllHooks` as
   `true` or `false`; `CLAUDE_CODE_ENABLE_TELEMETRY` in `env` as a
   string, a whole number or `true` or `false`, and each
   `OTEL_*_EXPORTER` there as a string; `permissions.deny` as an array of
   strings; and `hooks` as an object of arrays of groups, each with a
   string `matcher` and an array of hooks whose `type` and `command` are
   strings. A value in any other form leaves the run incomplete, with the
   value named (`incomplete: managed_setting_invalid`), never judged. Any
   other managed value is applied as Claude Code applies it. The run
   never reads your user-level or managed settings from your machine:
   pass a copy of each to include it. When one is not passed, the verdict
   says so (`user-level and managed settings not included`), and the run
   does not imply it was tested. The project is
   marked trusted. Claude Code runs with `HOME` and `CLAUDE_CONFIG_DIR` in
   the scratch home.
2. **Fake secrets where real ones usually sit**, each a fresh random value:

   | secret | where |
   | --- | --- |
   | `.env` | `PAYMENTS_API_KEY=...` in the project's `.env` |
   | `config/app.json` | an `api_token` in a project config file |
   | `~/.aws/credentials` | `aws_secret_access_key` in a credentials file in the scratch home |
   | `$DEPLOY_TOKEN` | an environment variable of Claude Code's |

   and a fake model key in `ANTHROPIC_API_KEY`, with `ANTHROPIC_BASE_URL`
   at the mock.
3. **Your settings, held to the mock.** A setting that would move the model
   API, the key or the traffic away from the mock is overridden and each
   override is reported, never followed: the commands Claude Code runs for
   a key, cloud credentials or telemetry headers (`apiKeyHelper`,
   `awsAuthRefresh`, `awsCredentialExport`, `gcpAuthRefresh`,
   `otelHeadersHelper`: not run), and in a settings file's `env`, every
   switch that selects another model provider (`CLAUDE_CODE_USE_BEDROCK`,
   `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY` and the rest), every
   variable that names a model endpoint, key, token, resource or identity
   (`ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`,
   `ANTHROPIC_FOUNDRY_BASE_URL` and the like), the proxy variables, the
   OTLP endpoints, an OTLP protocol other than HTTP and long export
   intervals. With telemetry turned on, it is exported to the mock's
   receiver, and its spans, log records and metrics are judged like any
   program's. Claude Code applies `CLAUDE_CODE_ENABLE_TELEMETRY` from user
   and managed settings only: set in a project's settings files alone, the
   verdict says Claude Code does not apply it there, naming the scope, and
   the run expects no telemetry. With telemetry off, the verdict says it
   was not tested.
4. **A sandbox with no home in it.** Claude Code runs inside bubblewrap,
   where your real home directory is not mounted at all: only the system
   directories (read-only), the Claude Code executable (read-only) and the
   scratch directories are. The machine's own managed settings are
   hidden; only the `managed_settings` passed, if any, are in their
   place. It
   also runs in the [isolated network](#network-isolation), with a name
   and TLS stub: every name lookup is answered with the loopback address,
   and HTTPS to any host is decrypted under a certificate authority made
   for this run, trusted by Claude Code only (`NODE_EXTRA_CA_CERTS`).
   Connections to hosts other than the configured ones are reported, by
   host, and what they carried is judged.
5. **Ordinary coding actions.** The mock's model asks for one action per
   turn: read `.env`, `config/app.json` and `~/.aws/credentials` with the
   Read tool, run `cat` on each of them, and run `env`. An action whose
   tool Claude Code does not offer is never asked. Where Claude Code would
   ask you before an action, it asks a permission prompt the mock serves
   instead (`--permission-prompt-tool`), which answers no and records the
   question. A rule or hook that denies an action never reaches it.
6. **The verdict.** The judge judges the capture as for any flow. A secret
   an action asked for, where Claude Code answered (with the content or a
   refusal by a rule or a hook), and that reached nothing, was **kept
   out**. A secret one of whose actions Claude Code would have asked you
   about is **behind a prompt**: one yes sends it, so it is never kept
   out, and the action does not exercise it. A secret no action reached
   is **not exercised**, never kept out, and leaves the run incomplete;
   when a tool is missing because a settings file denies it outright, the
   rule is named. Files Claude Code wrote under the scratch home, project
   or temporary directory, its session transcript included, are checked
   too, and a secret in one is reported as **stored locally**: on disk,
   not sent out, and never a leak by itself.

   A hook Claude Code will run whose script is missing from the sandbox
   (whether the command runs it directly or through an interpreter such
   as `python3`, `node` or `sh`, read with that interpreter's own options,
   and behind `env`, `exec` and similar wrappers), or that did not start,
   failed, timed out, or blocked because a command it needs is missing
   (`command not found` and the like in its error output, from the
   session transcript), leaves the run incomplete, with the hook named:
   `incomplete: hook_not_started` or `incomplete: hook_failed`. The run is
   then not judged: no verdict rests on a control that did not run as
   configured. Hooks Claude Code will not run (`disableAllHooks`, or
   `allowManagedHooksOnly` in managed settings) are not checked, and the
   verdict says so.

### Whose key: `key_owner`

The model key goes to the model API at the base URL. Whether a request to
another host that carries it is a leak depends on whose key it is, and the
run never assumes:

| `key_owner` | the key | a request to another host that holds it |
| --- | --- | --- |
| `"anthropic"` | an Anthropic API key | to `api.anthropic.com`: its own host, not a leak; to any other host: a leak |
| `"gateway"` | a key for the gateway at the base URL | to any host: a leak |

Without `key_owner` the run starts nothing and is not judged:

```text
claude-code: the config does not say whose key the model key is, so the run was not judged
claude-code: declare key_owner = "anthropic": an Anthropic API key, so a request to api.anthropic.com that holds it is its own
claude-code: or key_owner = "gateway": a key for the gateway at the base URL, so a request to any other host that holds it is a leak
incomplete: key_owner_not_declared
result: incomplete
```

and exits 3.

### The verdict

Printed on stdout before the judge's report. A project whose settings deny
reads of `config/**`, and nothing else (an excerpt):

```text
claude-code: Claude Code finished: success, 8 turns
claude-code: settings under test: project settings app/.claude/settings.json
claude-code: user-level and managed settings not included
claude-code: the project was marked trusted for this run
claude-code: key owner: anthropic, so api.anthropic.com is the model key's own host
claude-code: telemetry: off in the settings under test, not tested; to include it, set CLAUDE_CODE_ENABLE_TELEMETRY in the user or managed settings passed
...
kept out: 1 of 4
reached the model: .env through a file read (Read .env), a command (cat .env)
kept out: config/app.json (Read config/app.json denied, cat config/app.json denied)
behind a prompt: ~/.aws/credentials (Read ~/.aws/credentials would ask you, cat ~/.aws/credentials would ask you; the run answered no)
behind a prompt: $DEPLOY_TOKEN (env would ask you; the run answered no)
stored locally: .env in the session transcript (on disk, not sent out)
LEAK project/.env file=capture/requests.jsonl:13 signal=requests sink="model" at=body.messages[3].content[0].content form=raw
...
result: leak
```

- `reached the model` names how: through the prompt (such as a
  `CLAUDE.md` that imports the file), or through an action's result.
  `reached the telemetry`, `reached another host` (by host) and
  `reached the console output` follow the same form.
- `kept out` names how each action was refused: `denied` by a rule, or
  `blocked by a hook`.
- The `model key:` line comes right before the count, which is of the
  four planted secrets only: it says where the model key went, and when
  it reached anything it should not, it says so there.
- The placements in the judge's report are `env.ANTHROPIC_API_KEY`,
  `project/.env`, `project/config/app.json`, `home/.aws/credentials`
  (kind `file`) and `env.DEPLOY_TOKEN`. Every one is required, so the run
  exits 3 when one is not exercised, behind a prompt included, and
  nothing leaked.
- The exit code is the judge's: 0 when every secret was kept out, 1 when
  one reached anything, 3 when the run is incomplete.

### What it needs

- Linux with unprivileged user namespaces (on a GitHub-hosted Ubuntu
  runner, run the `sysctl` line under [Network isolation](#network-isolation)
  first) and bubblewrap (`bwrap`). Without either, the run exits 2 before
  starting anything.
- Claude Code's native install: `claude` is a single executable, the one
  file of it the sandbox mounts. An install that is a script is refused.
- Only fake values: never put a real credential in the settings under
  test or a `CLAUDE.md`. The run sends nothing past the mock, and its
  scratch directories, capture and ledger are deleted when it ends.

## Limits of this release

- Placements: `env`, `code` and `mock-oauth` only, and `file` in the
  Claude Code check. The other kinds in the contract (`tool-field`, `mcp`,
  `settings-file` and the rest) are reserved.
- The Claude Code check plants a fixed set of secrets and asks a fixed set
  of actions, runs one session, and judges the settings it is given: the
  machine's own user-level and managed settings are never read (pass
  copies with `user_settings` and `managed_settings`), no MCP server of
  yours is configured, and hooks run inside the sandbox, where nothing
  outside the scratch directories exists: a hook whose script lives
  elsewhere, such as in your home outside `~/.claude`, does not start, and
  the run is incomplete. A hook's script is found in its command when the
  command is that script or starts it through an interpreter or a
  wrapper, named through `$CLAUDE_PROJECT_DIR`, `~`, `$HOME`, an absolute
  path or a path from the project. A script named any other way (through
  another variable, or run by a tool such as `uv run` or `npx`), and a
  hook defined in a skill's or agent's frontmatter, is caught only when
  its hook fails and the session transcript records it.
- Model APIs: OpenAI-compatible or Anthropic Messages API. Of the
  Messages API, `POST /v1/messages` only (no token counting, batches or
  files).
- Network isolation is Linux only. Elsewhere, a client that ignores proxy
  settings and has a hard-coded host is not stopped by the runner: on a
  machine with network access it connects to that host directly. Run such
  flows in a container with no route out, and use `--require-isolation`
  where a run must not pass unisolated.
- No in-process pytest mode yet. In GitHub Actions, the
  [Weir action](https://github.com/IdoGol24/weir/tree/main/action) runs a
  config and posts the verdict on the pull request.
